## 왜 필요한가

2005년 즈음부터 클럭이 3~5 GHz에서 멈췄다. 전력이 대략 $P \propto C V^2 f$인데 전압을 더 못 낮추게 되면서(Dennard scaling의 종말) 클럭을 올리면 칩이 너무 뜨거워졌다 (power wall). 반면 트랜지스터 **개수**는 계속 늘었다. 남는 트랜지스터로 **동시에 여러 일을 하는 하드웨어**를 만드는 수밖에 없다.

| 방법 | Iron Law에서 공략하는 항 | 레슨 |
|---|---|---|
| **SIMD**: 명령어 하나로 데이터 여러 개 | IC ↓ (명령어 수를 8~16배 줄임) | 16 |
| **Multicore**: 명령어 흐름 여러 개 | 프로그램을 쪼개서 각자 실행 | 17 |
| **GPU**: 수천 thread를 SIMD식으로 묶음 | 위 두 개를 극단까지 | 18, 19 |

## 직관: 8칸짜리 도장

시험지 채점에서 스칼라 CPU는 한 장에 도장 하나를 찍는다. SIMD는 **8칸짜리 도장**이라 한 번 누르면 8장에 동시에 찍힌다. 단, 8장이 **나란히 놓여 있어야 하고**(연속 메모리), **전부 같은 도장**(같은 연산)을 받아야 한다.

```text
 Scalar:     a0+b0   a1+b1   a2+b2   ...   → 명령어 8개
 SIMD(8):   [a0 a1 a2 a3 a4 a5 a6 a7]
          + [b0 b1 b2 b3 b4 b5 b6 b7]
          = [c0 c1 c2 c3 c4 c5 c6 c7]      → 명령어 1개
```

## 병렬성의 종류

**ILP, Instruction-Level Parallelism (명령어 수준 병렬성)**: 한 명령어 흐름 안에서 독립적인 명령어를 겹쳐 실행 (pipelining, superscalar, out-of-order).

**DLP, Data-Level Parallelism (데이터 수준 병렬성)**: 같은 연산을 많은 데이터에 적용 (SIMD, GPU).

**TLP, Thread-Level Parallelism (스레드 수준 병렬성)**: 독립적인 명령어 흐름 여러 개를 동시에 실행 (multicore).

**Flynn's taxonomy**

| | Single Data | Multiple Data |
|---|---|---|
| **Single Instruction** | SISD (스칼라 CPU) | **SIMD** (벡터 유닛) |
| **Multiple Instruction** | MISD (거의 없음) | **MIMD** (multicore) |

## SIMD 정의

**SIMD (Single Instruction, Multiple Data)**: 명령어 하나가 벡터 레지스터 안의 여러 데이터 원소에 같은 연산을 동시에 적용하는 방식.
*A single instruction operates on multiple data elements packed in a wide register.*

**Vector register (벡터 레지스터)**: 여러 원소를 담는 넓은 레지스터 (128/256/512 bit).

**Lane (레인)**: 벡터 레지스터 안의 원소 하나의 자리. 256-bit는 float32 기준 8 lane.

**FMA, Fused Multiply-Add (융합 곱셈-덧셈)**: $d = a \times b + c$를 한 명령어로, 반올림 한 번에 계산. **2 FLOP**로 센다. 딥러닝의 MAC 연산 그 자체다.

| ISA | 폭 | FP32 lane | INT8 lane | 어디서 |
|---|---|---|---|---|
| SSE | 128 bit | 4 | 16 | x86 (오래됨) |
| AVX2 | 256 bit | 8 | 32 | 대부분의 x86 |
| AVX-512 | 512 bit | 16 | 64 | 서버, 일부 데스크톱 |
| NEON | 128 bit | 4 | 16 | ARM (스마트폰, Apple Silicon, RPi) |
| Helium (MVE) | 128 bit | 4 | 16 | Cortex-M55/M85 (MCU) |

### Peak FLOPS

$$
\text{Peak FLOP/s} = (\text{cores}) \times f \times (\text{SIMD lanes}) \times (\text{FMA units / core}) \times 2
$$

### SIMD가 잘 동작하는 조건

1. **데이터가 연속**이어야 한다. stride가 있으면 gather 명령어가 필요하고 훨씬 느리다 (10번 레슨).
2. **반복 간 의존성이 없어야** 한다. `a[i] = a[i-1] + x`처럼 앞 결과가 필요하면 8개를 동시에 못 한다 (05번 레슨의 RAW).
3. **분기가 없거나 마스크로 바꿀 수 있어야** 한다. `if`는 양쪽을 다 계산하고 마스크로 고르는(blend) 방식으로 바꾼다.
4. **정렬(alignment)**: 주소가 32 B/64 B 배수면 load가 더 효율적이다.

**Auto-vectorization (자동 벡터화)**: 컴파일러가 스칼라 루프를 SIMD 명령어로 자동 변환하는 것. 조건 1~3이 명확할 때만 동작한다.

**Intrinsics (인트린식)**: SIMD 명령어를 C 함수처럼 직접 호출하는 방법. 예: `_mm256_fmadd_ps(a, b, c)`

## Reduction과 누적기

`sum += a[i] * b[i]`는 `sum`에 대한 loop-carried dependency가 있다. 벡터화해도 누적 레지스터가 하나면 FMA가 이전 FMA 결과를 기다려야 한다. FMA latency가 $L$ 사이클이고 코어가 사이클당 $R$개의 FMA를 시작할 수 있으면, 파이프라인을 꽉 채우는 데 필요한 독립 누적기 수는 **Little's law**로

$$
\text{필요한 누적기 수} = L \times R
$$

FMA latency 4, FMA 유닛 2개면 **8개**가 필요하다. 05번 레슨에서 HLS dot product를 `psum[4]`로 나눈 것과 같은 원리다.

<Aside type="caution" title="컴파일러가 reduction을 벡터화 못 하는 이유">
부동소수점은 덧셈 결합법칙이 정확히 성립하지 않는다($(a+b)+c$와 $a+(b+c)$가 다를 수 있음). 그래서 컴파일러는 reduction 순서를 마음대로 못 바꾸고, `-O3`만으로는 `sum +=` 루프가 벡터화되지 않는 경우가 많다. `-ffast-math`를 주거나 직접 누적기를 나눠야 한다.
</Aside>

## Worked example: peak와 dot product 실측

**(a) Peak** (가상의 데스크톱: 8 cores, 3 GHz, AVX2, FMA 유닛 2개/core)

$$
8 \times 3 \times 10^9 \times 8 \times 2 \times 2 = 768 \text{ GFLOP/s}
$$

스칼라, FMA 없음, 코어 1개로 사이클당 1연산만 하면 3 GFLOP/s. **256배 차이**가 SIMD + FMA + multicore에서 온다.

**(b) 실측** (N = 4096 float, 16 KB 배열 2개가 L1에 상주, 클라우드 Xeon, AVX2 + FMA)

```text
scalar                   1.63 GFLOP/s
AVX2 FMA, 1 acc         13.78 GFLOP/s
AVX2 FMA, 8 acc         46.03 GFLOP/s
```

측정값을 역산하면 turbo 클럭이 대략 3.3 GHz다. FMA latency를 4 사이클로 두고 각 결과를 설명하면

| 버전 | 병목 | 사이클당 FLOP | 3.3 GHz 예측 | 실측 |
|---|---|---|---|---|
| Scalar | `s +=` 의존성 → 4 사이클마다 곱+덧셈 하나 | 2 / 4 = 0.5 | 1.65 | 1.63 |
| AVX2, 누적기 1개 | 4 사이클마다 8-lane FMA 하나 | 16 / 4 = 4 | 13.2 | 13.78 |
| AVX2, 누적기 8개 | **load port**: FMA마다 벡터 load 2개, 사이클당 load 2개 → 사이클당 FMA 1개 | 16 | 52.8 | 46.03 |

읽어낼 것:
1. 누적기 1개 → 8개만으로 **3.3배**. 하드웨어는 같고 **의존성만 끊었다.**
2. 누적기 8개 버전은 FMA 유닛 한계(사이클당 32 FLOP)가 아니라 **L1에서 데이터를 가져오는 속도**에 막힌다. dot product는 2 FLOP마다 float 2개(8 B)를 읽어야 하기 때문이다. "연산당 데이터 양"이 성능 상한을 정한다는 게 roofline 모델의 핵심이다.
3. Scalar → 최적 SIMD = **28배**. 코어 하나에서 나온 차이다.

<Aside type="note" title="숫자는 기계마다 다르다">
load port 수는 CPU 세대마다 다르고(최신 코어는 사이클당 load 3개도 가능), turbo 클럭도 그때그때 바뀐다. 같은 클라우드 VM에서 아래 C 코드를 다시 돌렸을 때는 8 acc 버전이 67 GFLOP/s까지 나오기도 했다. 비율(scalar ≪ 1 acc ≪ 8 acc)과 병목의 종류가 핵심이다.
</Aside>

## 코드

### Python: dtype별 처리량

```python
import time
import numpy as np

def best(f, reps=3):
    t_best = float("inf")
    for _ in range(reps):
        t = time.perf_counter(); f(); t_best = min(t_best, time.perf_counter() - t)
    return t_best

# c = a*b + c, 64K elems (cache-resident), 2000 reps
n, reps = 1 << 16, 2000
for dt in [np.float64, np.float32, np.float16]:
    a = np.random.rand(n).astype(dt); b = np.random.rand(n).astype(dt); c = np.zeros(n, dt)
    tmp = np.empty(n, dt)
    def f():
        for _ in range(reps):
            np.multiply(a, b, out=tmp); np.add(tmp, c, out=c)
    t = best(f)
    print(f"{np.dtype(dt).name:8s} {2*n*reps/t/1e9:6.2f} GFLOP/s   ({np.dtype(dt).itemsize} B/elem)")
```

실측 예: float64 1.75, float32 8.37, **float16 0.12** GFLOP/s.

- float32가 빠른 이유: 같은 벡터 레지스터에 lane이 2배고, 옮길 byte도 절반이다.
- float16이 70배 느린 이유: 이 CPU에는 FP16 **산술** SIMD 명령어가 없어서 원소마다 float32로 변환해서 계산하고 다시 변환한다.

### C: 누적기 1개 vs 8개 (x86 AVX2 전용)

```c
// gcc -O3 -march=native dot.c -o dot && ./dot
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <immintrin.h>
#define N 4096
#define REPS 200000
static float a[N] __attribute__((aligned(64))), b[N] __attribute__((aligned(64)));
static double now(void) { struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); return t.tv_sec + t.tv_nsec * 1e-9; }

__attribute__((optimize("no-tree-vectorize")))
float dot_scalar(void) { float s = 0; for (int i = 0; i < N; i++) s += a[i] * b[i]; return s; }

float dot_1acc(void) {          // 매 FMA가 직전 FMA 결과를 기다림
    __m256 acc = _mm256_setzero_ps();
    for (int i = 0; i < N; i += 8)
        acc = _mm256_fmadd_ps(_mm256_load_ps(a + i), _mm256_load_ps(b + i), acc);
    float t[8]; _mm256_storeu_ps(t, acc);
    return t[0]+t[1]+t[2]+t[3]+t[4]+t[5]+t[6]+t[7];
}

float dot_8acc(void) {          // 독립 FMA 8개가 파이프라인에 동시에
    __m256 c[8];
    for (int k = 0; k < 8; k++) c[k] = _mm256_setzero_ps();
    for (int i = 0; i < N; i += 64)
        for (int k = 0; k < 8; k++)
            c[k] = _mm256_fmadd_ps(_mm256_load_ps(a + i + 8*k), _mm256_load_ps(b + i + 8*k), c[k]);
    for (int k = 1; k < 8; k++) c[0] = _mm256_add_ps(c[0], c[k]);
    float t[8]; _mm256_storeu_ps(t, c[0]);
    return t[0]+t[1]+t[2]+t[3]+t[4]+t[5]+t[6]+t[7];
}

static void bench(const char *name, float (*f)(void)) {
    volatile float sink = 0; double t = now();
    for (int r = 0; r < REPS; r++) { sink += f(); __asm__ volatile("" ::: "memory"); }
    t = now() - t;
    printf("%-16s %7.2f GFLOP/s\n", name, 2.0 * N * REPS / t / 1e9);
}

int main(void) {
    for (int i = 0; i < N; i++) { a[i] = rand() / (float)RAND_MAX; b[i] = rand() / (float)RAND_MAX; }
    bench("scalar", dot_scalar); bench("AVX2, 1 acc", dot_1acc); bench("AVX2, 8 acc", dot_8acc);
}
```

Apple Silicon(ARM)에서는 AVX2 intrinsics가 없어서 컴파일이 안 된다.

## 흔한 오해

<Aside type="caution" title="비트 수를 줄이면(FP16, INT8) 무조건 빨라진다?">
하드웨어가 그 타입의 SIMD/행렬 연산을 지원할 때만 그렇다. 위 float16 결과(70배 느림)가 반례다.
</Aside>

<Aside type="caution" title="벡터화만 하면 peak가 나온다?">
누적기 1개 버전은 SIMD를 쓰는데도 peak의 15% 정도였다. 의존성(latency)과 load 대역폭이 추가로 상한을 만든다.
</Aside>

## Efficient ML 연결

**Quantization = 같은 SIMD 폭에 더 많은 lane.** 256-bit 레지스터에 FP32는 8개, **INT8은 32개**다. 같은 명령어 수로 4배의 MAC을 처리하고 메모리에서 옮길 byte도 1/4이다. INT8 quantization이 CPU/MCU에서 빨라지는 하드웨어적 이유다. 반대로 **INT4**는 대부분 하드웨어에 네이티브 연산이 없어서 두 개씩 패킹했다가 풀어야 한다 (unpack 오버헤드).

**MCU의 SIMD.** Cortex-M4/M7의 DSP 확장에는 32-bit 레지스터에 16-bit 값 두 개를 넣고 **MAC 2개를 한 명령어로** 하는 `SMLAD` 같은 명령어가 있다. Arm의 **CMSIS-NN**이 이걸로 INT8/INT16 conv를 가속한다. Cortex-M55/M85의 **Helium**은 MCU용 128-bit 벡터 확장이다.

**TinyEngine.** MIT 6.5940의 커널 최적화 목록에 SIMD programming이 들어 있다. 이 레슨의 누적기 분리, 연속 접근, 정렬이 그대로 쓰인다.
