## 왜 필요한가

`beq x1, x2, LABEL`이 분기할지는 비교를 해봐야 안다. 5-stage에서 비교는 EX에서 일어나는데, IF는 매 사이클 **다음** 명령어를 가져와야 한다. "어디서 가져오지?"를 모르는 상태다. 프로그램에서 분기는 대략 명령어 5~6개 중 하나꼴로 나오므로, 분기마다 기다리면 파이프라인의 이득이 크게 줄어든다.

## 용어 정의

**Control hazard (제어 해저드, branch hazard)**: 분기 결과가 결정되기 전에 다음 명령어를 fetch해야 하는 상황.
*A hazard arising from the need to make a decision based on the result of one instruction while others are executing.*

**Flush (플러시)**: 잘못 가져온 명령어를 파이프라인에서 제거(nop으로 바꿈)하는 것.
*Discarding instructions in the pipeline, usually due to a misprediction.*

**Branch prediction (분기 예측)**: 분기 결과를 미리 추측해서 결과가 나오기 전에 실행을 이어가는 기법.
*Predicting the outcome of a branch and proceeding from that assumption rather than waiting.*

**Branch misprediction penalty (분기 예측 실패 페널티)**: 예측이 틀렸을 때 버려지는 사이클 수. 분기 결과가 파이프라인의 몇 번째 stage에서 결정되는지에 비례한다.
*The number of cycles lost when a branch is mispredicted.*

## 해결책 1: Stall

분기 결과가 나올 때까지 fetch를 멈춘다. 단순하지만 **모든 분기**에 penalty가 생긴다.

## 해결책 2: Predict-not-taken (정적 예측)

일단 분기 안 한다고 가정하고 PC+4 명령어를 계속 가져온다. 틀리면(실제로 분기하면) 잘못 가져온 명령어를 flush한다.

```text
사이클             1    2    3    4    5    6
beq x1,x2,L       IF   ID   EX   ←── 여기서 "taken" 판명
(PC+4 명령어)          IF   ID   ✗flush
(PC+8 명령어)               IF   ✗flush
L: (목적지)                       IF   ID  ...     → 2 사이클 penalty
```

분기하지 않는 경우에는 손해가 0이고, 분기하는 경우에만 2 사이클을 잃는다.

## 해결책 3: Dynamic branch prediction

과거 실행 기록을 보고 예측한다.

**1-bit predictor**: "지난번에 taken이었으면 이번에도 taken." 루프가 끝날 때 한 번 틀리고, 다시 루프에 들어올 때 또 한 번 틀려서 **루프를 한 번 돌 때마다 2번** 틀린다.

**2-bit saturating counter**: 두 번 연속 틀려야 예측을 바꾼다. 루프 끝에서 **1번만** 틀린다.

```text
       taken           taken           taken
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌───────────┐
  │ 00       │───▶│ 01       │───▶│ 10       │───▶│ 11        │──┐ taken
  │ strong N │    │ weak N   │    │ weak T   │    │ strong T  │◀─┘
  └──────────┘◀───└──────────┘◀───└──────────┘◀───└───────────┘
   ▲   │ not       not taken       not taken       not taken
   └───┘ taken
   predict: Not-taken ◀────────┃────────▶ predict: Taken
```

안쪽 루프가 $n$번 도는 경우 정상 상태 정확도는 대략

$$
\text{1-bit} \approx \frac{n-2}{n}, \qquad \text{2-bit} \approx \frac{n-1}{n}
$$

루프가 짧을수록 차이가 크다 ($n = 4$면 50% vs 75%).

<Aside type="note" title="예측하려면 목적지도 알아야 한다">
"taken"으로 예측하려면 분기 목적지 주소도 IF 단계에서 알아야 한다. 그래서 실제 CPU는 최근 분기의 목적지를 저장하는 BTB(Branch Target Buffer)를 같이 둔다.
</Aside>

## CPI 공식

이상적인 파이프라인은 CPI = 1이고, stall이 생기면

$$
CPI_{pipe} = 1 + \sum_{\text{hazard 종류}} (\text{발생 빈도}) \times (\text{발생 확률}) \times (\text{penalty})
$$

Branch만 떼어 보면

$$
\Delta CPI_{branch} = f_{branch} \times \text{misprediction rate} \times \text{penalty}
$$

## 깊은 pipeline의 trade-off

stage를 더 잘게 쪼개면 각 stage가 짧아져서 $T_{clk}$가 줄어든다(클럭 상승). 하지만

- register 오버헤드 비중이 커지고,
- 분기 결과가 더 뒤에서 결정되니 **misprediction penalty가 커지고**,
- load-use 같은 데이터 hazard의 stall도 길어진다.

Pentium 4가 20~31 stage까지 깊어졌다가 전력과 penalty 문제로 이후 세대에서 다시 얕아진 것이 대표적인 사례다.

## Worked example: 4가지 설계 비교

명령어 구성:
- Load 25%, 그중 40%는 바로 다음 명령어가 load 결과를 사용 (load-use)
- Branch 15%, 그중 60%가 taken

**설정 A: 5-stage, 1 GHz, predict-not-taken**
- load-use penalty 1, branch는 EX에서 결정 → misprediction penalty 2
- predict-not-taken이므로 taken인 경우가 전부 오예측 → misprediction rate = 60%

$$
CPI = 1 + 0.25 \times 0.4 \times 1 + 0.15 \times 0.6 \times 2 = 1 + 0.10 + 0.18 = 1.28
$$

**설정 B: 5-stage, 1 GHz, 2-bit predictor (정확도 90%)**

$$
CPI = 1 + 0.10 + 0.15 \times 0.1 \times 2 = 1.13
$$

**설정 C: 15-stage, 2.5 GHz, predict-not-taken** (load-use penalty 3, misprediction penalty 10으로 가정)

$$
CPI = 1 + 0.25 \times 0.4 \times 3 + 0.15 \times 0.6 \times 10 = 1 + 0.30 + 0.90 = 2.20
$$

**설정 D: 15-stage, 2.5 GHz, 2-bit predictor 90%**

$$
CPI = 1 + 0.30 + 0.15 \times 0.1 \times 10 = 1.45
$$

| 설정 | CPI | Clock | ns/inst | A 대비 |
|---|---|---|---|---|
| A: 5-stage, not-taken | 1.28 | 1 GHz | 1.28 | 1.00× |
| B: 5-stage, 2-bit | 1.13 | 1 GHz | 1.13 | 1.13× |
| C: 15-stage, not-taken | 2.20 | 2.5 GHz | 0.88 | 1.45× |
| D: 15-stage, 2-bit | 1.45 | 2.5 GHz | 0.58 | 2.21× |

읽어낼 것:

1. C는 A보다 **CPI가 1.72배 나쁜데도 더 빠르다.** CPI만 보면 안 된다 (Iron Law).
2. Branch predictor 개선 효과가 5-stage에서는 1.13배(A → B)인데 15-stage에서는 **1.52배**(C → D)다. 깊은 pipeline일수록 예측 정확도가 훨씬 중요해진다.
3. Amdahl 관점: C에서 branch가 CPI의 $0.90 / 2.20 \approx 41\%$를 차지한다. 여기를 공략하는 게 맞다.

## 코드: CPI 모델과 predictor 시뮬레이터

```python
def cpi(f_load, p_use, pen_use, f_br, mispred, pen_br):
    return 1 + f_load * p_use * pen_use + f_br * mispred * pen_br

configs = [
    ("A 5-stage not-taken",  1.0e9, cpi(0.25, 0.4, 1, 0.15, 0.6, 2)),
    ("B 5-stage 2-bit",      1.0e9, cpi(0.25, 0.4, 1, 0.15, 0.1, 2)),
    ("C 15-stage not-taken", 2.5e9, cpi(0.25, 0.4, 3, 0.15, 0.6, 10)),
    ("D 15-stage 2-bit",     2.5e9, cpi(0.25, 0.4, 3, 0.15, 0.1, 10)),
]
base_t = configs[0][2] / configs[0][1]
for name, f, c in configs:
    tt = c / f
    print(f"{name:22s} CPI={c:.2f}  {tt*1e9:.2f} ns/inst  speedup={base_t/tt:.2f}x")

def accuracy(outcomes, bits):
    hit = 0
    if bits == 1:
        state = 0                             # 0: N, 1: T
        for o in outcomes:
            hit += (state == o)
            state = o
    else:
        state = 1                             # 0,1 → predict N / 2,3 → predict T
        for o in outcomes:
            hit += ((state >= 2) == o)
            state = min(3, state + 1) if o else max(0, state - 1)
    return hit / len(outcomes)

print("\nLoop branch (T...T N 반복)")
for n in [4, 10, 100]:
    pattern = ([1] * (n - 1) + [0]) * 1000    # 안쪽 루프 n번: backward branch가 T n-1번, 마지막 N
    print(f"inner loop={n:3d}  1-bit={accuracy(pattern, 1)*100:5.1f}%  "
          f"2-bit={accuracy(pattern, 2)*100:5.1f}%")
```

## 흔한 오해

<Aside type="caution" title="파이프라인은 깊을수록 좋다?">
클럭은 올라가지만 misprediction penalty, load-use penalty, register 오버헤드, 전력이 다 늘어난다. 최적 깊이가 존재한다.
</Aside>

<Aside type="caution" title="예측이 틀리면 결과가 틀린다?">
아니다. 예측이 틀리면 잘못 가져온 명령어를 **flush하고 다시** 실행하므로 결과는 항상 맞다. 잃는 건 **시간**뿐이다.
</Aside>

## Efficient ML 연결

**Speculative decoding = branch prediction.** LLM decoding은 token $t+1$이 token $t$에 의존하는 RAW 의존성의 연속이다. Speculative decoding은 CPU branch prediction과 구조가 똑같다.

| CPU | Speculative decoding |
|---|---|
| Branch predictor | 작은 draft model이 다음 토큰 여러 개를 예측 |
| 분기 결과 확인 (EX) | 큰 target model이 한 번의 forward pass로 검증 |
| Flush | 틀린 지점 이후의 draft 토큰을 버림 |
| 결과는 항상 정확 | 출력 분포가 target model과 같음 (rejection sampling) |
| 예측 정확도 × penalty | acceptance rate × draft 비용 |

위 worked example의 "빈도 × 오예측률 × penalty" 프레임으로 기대 speedup을 모델링할 수 있다. 예측 정확도가 높을수록, 틀렸을 때 손해(draft 생성 비용)가 작을수록 이득이 커진다.

**LLM agent의 speculative tool call.** tool 실행 결과를 기다리는 시간이 stall이고, 결과를 미리 추측해서 다음 행동을 시작하는 게 speculative execution이며, 틀리면 rollback하는 게 flush다. 같은 틀로 분석할 수 있다.

## 서술형

### 문제. 깊은 pipeline에 필요한 예측 정확도

12-stage pipeline CPU에서 분기 결과가 늦게 결정되어 misprediction penalty가 8 사이클이다. 명령어의 18%가 branch이고, 그중 65%가 taken이다. branch 외의 stall은 없다고 가정한다 (기본 CPI 1).

(a) predict-not-taken일 때 CPI는?

(b) 정확도 92%인 2-bit predictor를 쓰면 CPI는? (a) 대비 speedup은?

(c) branch로 인한 CPI 증가를 0.05 이하로 만들려면 predictor 정확도가 몇 % 이상이어야 하나?

(d) 같은 계산을 speculative decoding에 적용해 보자. draft model이 토큰 $\gamma = 4$개를 제안하고, target model이 한 번의 forward pass로 검증한다. 각 draft 토큰이 받아들여질 확률이 $\alpha = 0.7$로 서로 독립이고, 처음 거부된 토큰부터 뒤는 전부 버린다. 검증 한 번마다 target model이 항상 토큰 1개를 직접 만든다고 할 때, forward pass 한 번에 얻는 토큰 수의 기댓값은?

<details>
<summary>풀이 보기</summary>

**(a)** taken 분기가 전부 오예측이므로

$$
CPI = 1 + 0.18 \times 0.65 \times 8 = 1 + 0.936 = 1.936
$$

CPI의 거의 절반이 branch penalty다.

**(b)** 오예측률 8%:

$$
CPI = 1 + 0.18 \times 0.08 \times 8 = 1.115, \qquad \text{speedup} = \frac{1.936}{1.115} \approx 1.74
$$

**(c)** $0.18 \times (1 - a) \times 8 \le 0.05$에서 $1 - a \le 0.0347$, 즉 $a \ge 96.5\%$. penalty가 클수록 남은 몇 %의 오예측도 비싸져서, 깊은 pipeline에는 아주 정확한 predictor가 필요하다.

**(d)** $i$번째 draft 토큰은 앞의 $i$개가 모두 받아들여져야 남으므로 받아들여질 확률이 $\alpha^i$다. 여기에 target model이 만드는 토큰 1개를 더하면

$$
E = 1 + \alpha + \alpha^2 + \alpha^3 + \alpha^4 = \frac{1 - \alpha^{5}}{1 - \alpha} = \frac{1 - 0.168}{0.3} \approx 2.77
$$

forward pass 한 번에 평균 약 2.77개 토큰을 얻는다. CPU에서 예측 정확도와 penalty가 CPI를 정하듯, 여기서는 acceptance rate $\alpha$와 draft 비용이 speedup을 정한다.

</details>
