## 왜 필요한가

딥러닝 워크로드는 독립적인 MAC이 수십억 개다. CPU는 소수의 크고 똑똑한 코어로 명령어 하나를 최대한 빨리 처리하도록 설계됐고, GPU는 단순한 연산 유닛 수천 개로 **전체 처리량**을 극대화하도록 설계됐다. 2012년 AlexNet이 GPU 2장으로 학습되면서 딥러닝 붐이 시작됐다. 하지만 GPU는 조건이 맞을 때만 빠르다. thread들이 같은 길로 가야 하고, 충분히 많아야 한다.

## 직관: 32명씩 묶인 군대

GPU는 단순한 작업자 수천 명이다. 32명이 한 조(**warp**)이고, 조장이 구령(명령어) 하나를 외치면 32명이 **동시에 같은 동작**을 한다.

- 갈림길에서 16명은 왼쪽, 16명은 오른쪽으로 가야 하면? 구령이 하나뿐이라 왼쪽 팀을 먼저 보내고 오른쪽 팀은 **대기**, 그다음 오른쪽 팀을 보낸다. → **warp divergence**
- 어떤 조가 보급(메모리)을 기다리는 동안 지휘관은 **바로 다른 조**에게 구령을 내린다. → **latency hiding**

**CPU vs GPU = 스포츠카 vs 버스** (01번 레슨)

```text
        CPU (latency 최적화)                    GPU (throughput 최적화)
 ┌──────────────────────────────┐      ┌────────────────────────────────────┐
 │ ┌────────┐ ┌────────┐        │      │ ┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐   │
 │ │ Core   │ │ Core   │  큰    │      │ │SM││SM││SM││SM││SM││SM││SM││SM│   │
 │ │(OoO,   │ │        │ cache  │      │ └──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘   │
 │ │ branch │ │        │ (L3)   │      │ ┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐   │
 │ │ pred)  │ │        │        │      │ │SM││SM││SM││SM││SM││SM││SM││SM│   │
 │ └────────┘ └────────┘        │      │ └──┘└──┘└──┘└──┘└──┘└──┘└──┘└──┘   │
 │ ┌────────┐ ┌────────┐        │      │   ... 수십~100여 개 SM               │
 │ │ Core   │ │ Core   │        │      │ 작은 L2,  아주 넓은 메모리 버스(HBM)    │
 │ └────────┘ └────────┘        │      └────────────────────────────────────┘
 └──────────────────────────────┘
  소수의 크고 똑똑한 코어                  다수의 작고 단순한 연산 유닛
  latency를 cache와 예측으로 줄임           latency를 thread 전환으로 숨김
```

## 하드웨어 용어 (NVIDIA 기준)

**SM, Streaming Multiprocessor (스트리밍 멀티프로세서)**: GPU의 기본 연산 블록. CPU의 "코어"에 해당. warp scheduler 여러 개, 연산 유닛 수십~백여 개, 큰 register file, shared memory를 가진다.

**CUDA core**: SM 안의 스칼라 FP32/INT ALU **lane 하나**. CPU 코어와 대응하지 않는다.

**Tensor Core (텐서 코어)**: 작은 행렬 곱-누적(MMA)을 한 명령어로 수행하는 전용 유닛. FP16/BF16/INT8/FP8 등 낮은 정밀도를 지원.

**HBM / GDDR**: GPU 전용 고대역폭 메모리. CPU DRAM보다 대역폭이 수~수십 배 크다.

## 프로그래밍 모델 (CUDA)

**Kernel (커널)**: GPU에서 많은 thread가 동시에 실행하는 함수.

**Thread block (스레드 블록, CTA)**: 같은 SM에서 실행되고 shared memory를 공유하는 thread 묶음 (예: 256 threads).

**Grid (그리드)**: 한 kernel 호출의 모든 block.

**Warp (워프)**: 하드웨어가 **같은 명령어를 동시에 실행**하는 32개 thread 묶음. block은 warp들로 쪼개져서 실행된다.

```text
 Grid
 ├── Block 0 ── Warp 0 (thread 0–31), Warp 1 (32–63), ... Warp 7 (224–255)
 ├── Block 1 ── ...
 └── ...
```

```cuda
__global__ void vec_add(const float *a, const float *b, float *c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // 전역 thread 번호
    if (i < n) c[i] = a[i] + b[i];                   // 마지막 block의 남는 thread 방지
}
// 호출: vec_add<<<(n + 255) / 256, 256>>>(a, b, c, n);
```

$$
i = \text{blockIdx.x} \times \text{blockDim.x} + \text{threadIdx.x}
$$

## SIMT와 warp divergence

**SIMT (Single Instruction, Multiple Threads)**: 프로그래머는 thread 하나의 코드를 쓰고, 하드웨어는 warp의 32 thread를 같은 명령어로 묶어 실행하는 방식. 각 thread는 자기 레지스터와 주소를 갖고 분기도 할 수 있다.
*Threads are written as scalar programs but executed in lockstep groups (warps).*

SIMD와의 차이: SIMD는 프로그래머가 "8개짜리 벡터"를 직접 다루고, SIMT는 thread 하나만 생각하면 하드웨어가 알아서 묶는다.

**Warp divergence (워프 분기)**: 같은 warp 안의 thread들이 분기에서 다른 경로를 택하면, 하드웨어가 각 경로를 **순차적으로** 실행하고 해당 경로가 아닌 thread는 마스크로 비활성화하는 현상.
*When threads in a warp take different branch paths, the paths execute serially with inactive lanes masked off.*

$$
\text{SIMD efficiency} = \frac{\text{실제로 일한 lane-cycle}}{\text{전체 lane-cycle}}
$$

<Aside type="tip" title="핵심">
divergence는 **같은 warp 안에서** 갈릴 때만 생긴다. warp 단위로 갈리면(`if ((tid / 32) % 2)`) 손해가 없다.
</Aside>

## Latency hiding과 occupancy

GPU는 cache가 작고 메모리 latency가 수백 사이클이다. 큰 cache로 latency를 줄이는 대신, **SM에 warp를 수십 개 올려놓고** 한 warp가 메모리를 기다리면 warp scheduler가 **다음 사이클에 바로 다른 warp**의 명령어를 실행한다. 모든 warp의 레지스터가 register file에 상주해서 전환 비용이 0이다.

**Occupancy (점유율)**: SM이 지원하는 최대 warp 수 대비 실제로 올라가 있는 warp 수의 비율.
*The ratio of active warps on an SM to the maximum supported.*

thread당 레지스터를 많이 쓰거나 block당 shared memory를 많이 쓰면 SM에 올릴 수 있는 warp 수가 줄어 occupancy가 떨어진다.

**Little's law로 보기**: 메모리 대역폭 $BW$를 다 쓰려면 동시에 진행 중인 데이터 양이

$$
\text{bytes in flight} = BW \times \text{latency}
$$

만큼 있어야 한다. GPU가 수만 개의 thread를 필요로 하는 근본 이유다.

## Worked example 1: thread 인덱싱

$N = 1{,}000{,}000$, blockDim = 256

- 필요한 block 수: $\lceil 1{,}000{,}000 / 256 \rceil = \lceil 3906.25 \rceil = 3907$
- 총 thread: $3907 \times 256 = 1{,}000{,}192$ → 192개가 남는다. 마지막 block에서는 $1{,}000{,}000 - 3906 \times 256 = 64$개만 일해야 하므로 `if (i < n)` 가드가 필요하다.
- blockIdx = 3, threadIdx = 37인 thread: $i = 3 \times 256 + 37 = 805$. block 안에서 warp 번호 $\lfloor 37 / 32 \rfloor = 1$, lane $37 \bmod 32 = 5$.

## Worked example 2: warp divergence

256 thread (= warp 8개), then / else 경로 각각 10 사이클

**(a) `if (tid % 2 == 0)`**: 모든 warp에서 짝/홀이 반반 → 모든 warp가 두 경로를 다 실행
→ warp당 20 사이클 × 8 = **160 warp-cycle**, 효율 **50%**

**(b) `if (tid < 16)`**: warp 0만 갈림, warp 1~7은 전부 else
→ $20 + 7 \times 10 = 90$ warp-cycle
→ 일한 lane-cycle = $16 \times 10 + 16 \times 10 + 7 \times 32 \times 10 = 2560$
→ 효율 = $2560 / (90 \times 32) \approx$ **88.9%**

**(c) `if ((tid / 32) % 2 == 0)`**: warp 단위로 갈림 → 어떤 warp도 내부에서 안 갈림
→ **80 warp-cycle**, 효율 **100%**

**(d) `if (x[tid] > 0)`, x가 랜덤**: (a)와 같아짐 → **50%**

같은 "절반은 then, 절반은 else"라도 **어떻게 갈리느냐**에 따라 2배 차이가 난다.

## Worked example 3: thread가 왜 그렇게 많이 필요한가

메모리 대역폭 1 TB/s, latency 500 ns (대략적인 가정)

$$
\text{bytes in flight} = 10^{12} \times 500 \times 10^{-9} = 500{,}000\text{ B}
$$

coalesced warp load 하나가 128 B이므로 $500{,}000 / 128 \approx 3906$개의 warp load가 **항상 동시에** 진행 중이어야 한다. SM이 80개라면 SM당 약 49개다. warp 하나가 load 하나만 걸어놓고 기다린다면 SM당 warp 49개 이상이 올라가 있어야 대역폭을 다 쓴다.

## 코드: SIMT divergence 시뮬레이터

```python
import random
WARP = 32

def simt_cycles(cond, cost_then, cost_else):
    """warp 안에서 cond가 갈리면 두 경로를 순서대로 실행 (mask로 일부 lane만 활성)"""
    total, busy = 0, 0
    for w in range(0, len(cond), WARP):
        c = cond[w:w + WARP]
        n_then = sum(c); n_else = WARP - n_then
        if n_then: total += cost_then; busy += n_then * cost_then
        if n_else: total += cost_else; busy += n_else * cost_else
    return total, busy / (total * WARP)

random.seed(0)
T = 256
cases = {
    "if (tid % 2 == 0)":          [t % 2 == 0 for t in range(T)],
    "if (tid < 16)":              [t < 16 for t in range(T)],
    "if ((tid / 32) % 2 == 0)":   [(t // 32) % 2 == 0 for t in range(T)],
    "if (x[tid] > 0), 랜덤":       [random.random() > 0.5 for _ in range(T)],
}
for name, cond in cases.items():
    cyc, eff = simt_cycles(cond, 10, 10)
    print(f"{name:28s} warp-cycles={cyc:4d}  SIMD efficiency={eff*100:5.1f}%")

# thread 인덱싱
n, bd = 1_000_000, 256
blocks = (n + bd - 1) // bd
print(f"\nblocks={blocks}, total threads={blocks*bd}, last block active={n - (blocks-1)*bd}")
bi, ti = 3, 37
print(f"blockIdx={bi}, threadIdx={ti} -> i={bi*bd+ti}, warp={ti//32}, lane={ti%32}")

# Little's law
bw, lat = 1.0e12, 500e-9
print(f"\nbytes in flight = {bw*lat/1e3:.0f} KB = warp-load(128B) {bw*lat/128:,.0f}개")
```

## 흔한 오해

<Aside type="caution" title="GPU가 항상 CPU보다 빠르다?">
데이터가 작으면 PCIe 전송과 kernel launch 오버헤드가 더 크다. 분기가 많은 코드(divergence)나 불규칙한 메모리 접근도 GPU에서 느리다. batch = 1인 작은 모델 inference는 CPU가 더 빠른 경우도 흔하다.
</Aside>

<Aside type="caution" title="CUDA core 1개 = CPU core 1개?">
CUDA core는 **SIMD lane 하나**에 가깝다. CPU 코어와 대응하는 건 **SM**이다. "GPU 코어 1만 개 vs CPU 16코어" 같은 비교는 단위가 다르다.
</Aside>

<Aside type="caution" title="if문이 있으면 무조건 divergence?">
같은 warp 안의 thread들이 **다른 경로로 갈릴 때만** 생긴다. warp 단위로 갈리는 조건은 손해가 없다.
</Aside>

## Efficient ML 연결

**Tensor Core와 낮은 정밀도.** GPU에서 FP16/BF16/INT8/FP8 학습/추론이 빠른 이유는 Tensor Core가 그 타입의 행렬 곱을 한 명령어로 처리하기 때문이다. MIT 6.5940의 quantization 파트에서 "어떤 형식을 쓰느냐"는 결국 "어떤 Tensor Core 연산을 쓸 수 있느냐"와 연결된다.

**LLM decoding은 왜 GPU를 못 채우나.** batch = 1로 토큰 하나를 생성하면 행렬 곱이 사실상 **행렬 × 벡터**가 된다. 연산에 비해 읽을 weight가 너무 많고(memory-bound), 병렬로 처리할 일도 적어서 SM이 논다. 해결책:
- **Batching**: 여러 요청을 묶어 병렬성 증가 (vLLM)
- **Speculative decoding**: draft 토큰 여러 개를 **한 번에 병렬 검증**해서 놀던 연산 유닛을 쓴다

**Mixture of Experts와 divergence.** MoE는 토큰마다 다른 expert로 보낸다. 같은 batch 안에서 토큰들이 서로 다른 계산 경로로 가므로 warp divergence나 load imbalance와 비슷한 문제가 생긴다. 그래서 토큰을 expert별로 다시 모아서(permute) 각 expert가 dense 행렬 곱을 하게 만든다.
